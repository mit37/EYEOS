# EyeOS

> **v2 (2026 rebuild).** The original prototype's code was not preserved; this is a clean re-implementation of the same design. Numbers in this README come from this codebase.

Webcam eye tracking as an input device: MediaPipe gaze moves the Windows cursor behind a four-gate safety model.

## The thirty-second version

A regular webcam can estimate roughly where you're looking, but that estimate is too noisy to trust as a mouse — unless the system knows when *not* to act. EyeOS turns gaze into cursor movement, but only lets a click through after four independent safety gates agree: a real, confident, calibrated, stable gaze, with a kill switch and rate limits standing guard the whole time. The gates — not the gaze estimation — are the part of this project worth reading the code for.

## Results

Generated by `python -m eval.run_eval --fixtures eval/fixtures --out eval/results.json`, against the committed synthetic session (`eval/fixtures/synthetic_session.csv`, itself generated by `python -m eval.generate_synthetic` — deterministic, seeded, reproducible). CI runs this on every push.

| Metric | Value |
|---|---|
| Calibration validation error (leave-one-out RMS, 9-point grid) | 0.02 px |
| Mean pixel error, on-target frames, **raw** (no filter) | 29.8 px |
| Mean pixel error, on-target frames, **filtered** (One Euro) | 23.2 px |
| Mean angular error | **not measured** — this synthetic fixture has no real screen size or viewing distance to convert pixels into a visual angle with; a real recording would give this |
| Steady-state jitter, **raw** | 43.4 px |
| Steady-state jitter, **filtered** | 26.7 px |
| Gate false-accept rate on "looking away" frames (2 faces / low confidence / no face) | **0.0** (0 / 30) |
| Click false-trigger rate on a "just reading" hold (never confirmed) | **0.0** (0 / 300) |

A negative result, reported honestly per this project's own house rules: if you don't exclude each dwell block's first few frames from the jitter numbers (the One Euro filter is still *settling* toward a newly-switched target, which isn't jitter), the **filtered** jitter number comes out *higher* than the raw one — 88.6px vs 42.5px — even though the filter is clearly working (lower pixel error, and lower steady-state jitter once you look past the settling transient). `eval/run_eval.py`'s `notes.steady_state_jitter` explains the fix; both versions of the number are worth understanding if you're touching that code.

The calibration/filter numbers above are on synthetic, noiseless-except-injected-Gaussian iris offsets — they say the *pipeline's math is doing the right thing*, not what real webcam accuracy looks like. That number is marked "not measured" until Mitansh runs it on a real recording (see `docs/PLAN.md`'s "Cloud-instance constraints").

## Running it

No API key, no webcam required for the dry-run path:

```bash
git clone https://github.com/mit37/eyeos.git && cd eyeos
pip install -e .
eyeos run --config config.example.yaml            # dry-run over the synthetic fixture
python -m eval.run_eval                            # regenerate the Results numbers above
pytest                                              # 128 tests, no hardware needed
```

For a live session on real hardware (Windows + webcam): `pip install -e ".[webcam,windows-fallback]"`, copy `config.example.yaml` to `config.yaml`, set `input.source: webcam` and `output.backend: windows_sendinput`, then run the calibration UI before `eyeos run` — see `docs/DEMO.md`.

## Testing

```bash
pytest                       # run everything
pytest --cov=eyeos           # with coverage
ruff check . && black --check . && mypy eyeos   # lint + typecheck (CI runs these too)
```

**128 tests** (`pytest --collect-only -q | tail -1`), covering:

- The four-gate state machine gets the bulk of the suite (49 tests) — every gate's individual pass/fail conditions, the kill switch, no-click zones, click-rate limiting, dwell/jitter behavior, and confirmation (keypress and blink-hold), all driven by explicit timestamps rather than a wall clock, so the tests *are* a fake clock.
- Features, calibration (against a known synthetic ground-truth mapping), and the One Euro filter (against the reference algorithm's documented behavior) are each unit-tested in isolation.
- The full pipeline is tested end-to-end, both uncalibrated (gates correctly refuse to move) and calibrated (movement + a single click fire exactly where expected).
- Input sources, output adapters, the CLI, and the eval harness are tested down to their guarded "this dependency/hardware isn't available" paths, which is the actual code path this cloud container exercises.

## What this does not do

- **This is not an assistive-tech product.** It's a Tier-3 lab experiment in a four-gate safety model for noisy input. It has not been evaluated for accessibility use, has no certification, and shouldn't be trusted as anyone's only way to control a computer.
- **No real accuracy numbers yet.** Every number in Results above comes from a synthetic fixture, not a real webcam session. Real numbers are pending Mitansh recording sessions on real hardware (see `docs/PLAN.md`).
- **No webcam/video/Windows testing in this repo's CI.** Those code paths exist and are implemented (`eyeos/input_sources/webcam.py`, `video_file.py`, `output/windows_sendinput.py`), but this project was built in a cloud container with no camera, no display, and no Windows desktop — they're behind interfaces, guarded to fail with a clear error, and covered only on that guarded path.
- **No multi-monitor calibration.** Calibration targets the primary screen only (PRD non-goal, future work).
- **No typing / keyboard emulation.** EyeOS only moves the cursor and clicks.
- **The head-pose estimate is a simplified geometric approximation** (ratios of landmark positions scaled to degrees), not a camera-calibrated `solvePnP` fit. It's accurate enough for Gate 2's relative "has the pose drifted" check, not for absolute pose measurement.
- **Blink-hold confirmation and Gate 1's "both irises visible" check are in real tension** (a deliberate blink closes both eyes, which is also what Gate 1 watches for). The pipeline resolves it with a bounded grace window — see "Design decisions" below — rather than a literal reading of both PRD requirements at once.

## Design decisions

- **Gate 4 is one bundled boolean, not four independently wired sub-gates.** Kill switch, cursor-speed limit, click-rate limit, and no-click zones all gate *both* movement and clicking, exactly as the PRD's gate table states it — even though a real UI would probably only want no-click-zones and click-rate to block clicking, not movement. Trade-off: gazing near a no-click zone freezes the cursor entirely, which is stricter than necessary, but "one gate, one clear reason, one overlay light" is much easier to reason about, log, and test than four independently interacting movement/click rules.
- **Affine (degree-1) calibration by default, not degree-2 polynomial.** With only 9 calibration points, an affine model (5 parameters: 1 + 4 iris-offset numbers) is well-determined and recovers a clean mapping; the codebase supports `degree=2` for a closer fit, but that needs more/cleaner points to avoid ridge regression's minimum-norm solution picking an arbitrary split among collinear-ish higher-order terms. Trade-off: less accurate for genuinely non-linear gaze-to-screen mappings, more numerically predictable for a 9-point session.
- **The blink-hold confirmation gesture gets a dedicated grace window in `pipeline.py`, separate from Gate 1's eye-visibility check.** A literal reading of the PRD (both-eyes-closed as the click confirmation, but Gate 1 requiring both irises visible to allow movement at all) means a deliberate blink would freeze the cursor and cancel the dwell the instant the confirmation gesture starts — the click could never fire. The pipeline instead treats a closed-eye stretch of up to `confirmation_hold_s + 0.5s` as a deliberate gesture (still reports "visible" to Gate 1, accumulates hold duration), and only past that treats it as a genuine dropout. Trade-off: added complexity in `pipeline.py` (not `gates.py`, which stays a simple, literally-PRD-compliant state machine you can unit test with a fake clock).
- **Head pose is a simplified ratio-based estimate, not `cv2.solvePnP`.** Keeps `features.py` pure-numpy and unit-testable on hand-built fixture landmarks with no OpenCV/MediaPipe dependency at all. Trade-off: not camera-calibrated absolute angles, only good for relative "how far has this drifted" comparisons — which is exactly what Gate 2 needs.
- **The synthetic eval fixture is generated, seeded, and committed, not recorded.** `eval/generate_synthetic.py` builds a deterministic 465-frame session (calibration + noisy on-target dwells + three looking-away failure modes + a long unconfirmed "just reading" hold) entirely from hand-built landmark geometry — no video, no third-party data, reproducible with one command, and small enough (116 KB) to commit directly. Trade-off: it validates the pipeline's *logic*, not real-world webcam accuracy (see "What this does not do").
- **MediaPipe's legacy `solutions.face_mesh` API, not the newer Tasks `FaceLandmarker`**, in `webcam.py`/`video_file.py`. The Solutions API needs no separate model-file download, so `pip install eyeos[webcam]` is enough to run live — one less setup step for Mitansh's real-hardware demo. Trade-off: the Solutions API is in MediaPipe's legacy/maintenance track; a future pass could move to `FaceLandmarker` behind the same `InputSource` interface without touching any other module.
