## The thirty-second version

A regular webcam can estimate roughly where you're looking, but that estimate is too noisy to trust as a mouse — unless the system knows when *not* to act. EyeOS turns gaze into cursor movement, but only lets a click through after four independent safety gates agree: a real, confident, calibrated, stable gaze, with a kill-switch hotkey and rate limits standing guard the whole time. The gates — not the gaze estimation — are the part of this project worth reading the code for.

**Negative result: no intended click could fire on the noisy on-target gaze.** At the fixture's injected noise (σ = 0.03 in iris-offset units), the filtered frame-to-frame jitter is larger than Gate 3's 20 px dwell radius. So the 0.8 s dwell never holds on target, and no click of any kind could fire there. The "0 false clicks" row therefore has no matching hit rate. Whether real webcam noise is above or below this level is **not measured**. Either the noise would need to be lower, or `dwell_jitter_px` raised, before clicking is usable. That trade-off needs a real recording to settle.

**Correction to an earlier version of this README.** It reported a "negative result": filtered jitter of 88.6 px vs 42.5 px raw, blamed on the One Euro filter "settling". That was wrong. It was a bookkeeping bug in `eval/run_eval.py`, which compared each target block's second frame with the previous block's last cursor position. The bug is fixed, and raw and filtered are now measured over the same frames and the same frame pairs. The filter lowers both error and jitter in this fixture.

What these numbers mean: every metric here is a function of the injected noise, so they show that *the pipeline's math does what it should*, not what real webcam accuracy looks like. The raw on-target error is essentially that noise. Five of the six on-target dots are off the calibration grid, so it acts as a held-out error. Real-session numbers are pending recordings on real hardware (see `docs/PLAN.md`).

## Running it

No API key, no webcam required for the dry-run path:

```bash
git clone https://github.com/mit37/eyeos.git && cd eyeos
pip install -e ".[dev]"
eyeos run --config config.example.yaml            # dry-run over the synthetic fixture
python scripts/update_readme.py                    # regenerate every number in this README
pytest                                              # the full suite, no hardware needed
```

Live session on real hardware (Windows + webcam; the live extra needs **Python 3.10–3.12**, see below): `pip install -e ".[webcam,windows-fallback]"`, copy `config.example.yaml` to `config.yaml`, set `input.source: webcam` and `output.backend: windows_sendinput`, then:

```bash
eyeos run --config config.yaml --calibrate --overlay   # Esc (output.kill_hotkey) ends the session
```

`docs/DEMO.md` walks through it.


- The four-gate state machine has the largest share (<!-- gate-test-count -->69<!-- /gate-test-count --> tests). They cover every gate's pass/fail conditions, the kill switch, no-click zones, click-rate limiting, the speed limit, non-advancing timestamps, dwell/jitter behaviour and each confirmation mode. All of it is driven by explicit timestamps rather than a wall clock, so the tests *are* a fake clock.
- Features, calibration (against a known synthetic ground-truth mapping) and the One Euro filter (against the reference algorithm's documented behaviour) are each unit-tested in isolation.
- The full pipeline is tested end to end at 30 fps:
  - uncalibrated: the gates correctly refuse to move;
  - calibrated: one click fires exactly where expected;
  - a deliberate blink-hold click lands at the dwelled point;
  - the kill switch ends the session;
  - clicks never land inside a no-click zone after rounding or clamping.
- Hardware-only code runs against fakes: OpenCV/MediaPipe (`tests/fake_capture.py`), tkinter (`tests/fake_tk.py`) and the keyboard (`FakeKeySource`). These prove EyeOS's plumbing, not the libraries' real behaviour.

## What this does not do

- **This is not an assistive-tech product.** It's a Tier-3 lab experiment in a four-gate safety model for noisy input. It has not been evaluated for accessibility use, has no certification, and shouldn't be trusted as anyone's only way to control a computer.
- **No real accuracy numbers yet.** Every number in Results comes from a synthetic fixture, not a real webcam session. Real numbers, including the PRD's 5-minute reading false-click test, are pending recordings on real hardware (see `docs/PLAN.md`).
- **Nothing hardware-facing has run for real here.** Webcam/video capture, Windows `SendInput`, the pynput keyboard listener, the overlay and the calibration screen are all implemented. They are tested only against fakes, because this project was built in a cloud container with no camera, no display, no keyboard and no Windows desktop.
- **Live input needs MediaPipe < 0.10.30, so Python 3.10–3.12.** MediaPipe removed the legacy Solutions API (`mediapipe.solutions.face_mesh`) in 0.10.30, so the `webcam` extra pins below it, and those wheels stop at Python 3.12. Porting to the Tasks `FaceLandmarker` is future work.
- **Webcam timestamps come from the host clock.** They are taken when a frame arrives, because `CAP_PROP_POS_MSEC` is constant on live DirectShow/AVFoundation cameras. That behaviour was reasoned from OpenCV's source and not tested on hardware. A clock that doesn't advance fails Gate 1 instead of silently freezing the timers.
- **Gate 1's confidence check is enforced inside MediaPipe on real input.** The legacy API has no per-face score, so the threshold is passed to MediaPipe's detection and tracking thresholds. A face below it arrives as "no face", and the "confidence below threshold" reason only ever appears on synthetic input.
- **Glancing off the screen with your eyes alone isn't rejected.** If your head stays still, no gate fails: the gaze is clamped to the screen edge and the cursor follows it there. A click still needs dwell plus confirmation. Results reports this mode separately (the PRD's gate table has no on-screen check, and adding one would be new scope).
- **A natural eye closure can click.** In `blink_hold`/`either` mode, if your eyes stay closed for at least `confirmation_hold_s` (0.4 s) while a dwell is satisfied, that counts as a deliberate blink-hold, and a long natural blink would click. Use `confirmation_mode: keypress` to rule this out.
- **Calibrations aren't saved.** `--calibrate` runs once per session, by design ("a calibration exists for this session").
- **Not DPI-aware.** `config.screen` must equal the size the OS reports for the primary screen after display scaling (a 1920x1080 panel at 125% reports 1536x864). The calibration screen and the `SendInput` backend refuse to start on a mismatch rather than drawing dots off-screen.
- **No multi-monitor calibration.** Calibration targets the primary screen only (PRD non-goal, future work).
- **No typing / keyboard emulation.** EyeOS only moves the cursor and clicks.
- **The head-pose estimate is a simplified geometric approximation** (ratios of landmark positions scaled to degrees), not a camera-calibrated `solvePnP` fit. It's accurate enough for Gate 2's relative "has the pose drifted" check, not for absolute pose measurement.

## Design decisions

- **Gate 4 is one bundled boolean, not four independently wired sub-gates.** The kill switch, cursor-speed limit, click-rate limit and no-click zones all gate *both* movement and clicking, exactly as the PRD's gate table states. A real UI would probably let no-click zones and the click-rate limit block only clicks. Trade-off: gazing near a no-click zone freezes the cursor entirely, which is stricter than necessary. In return, "one gate, one clear reason, one overlay light" is much easier to reason about, log and test than four interacting rules. The gates also judge the exact rounded, on-screen pixel that will be sent, not the float gaze it came from.
- **The kill switch latches, and real-cursor output fails closed without it.** One press of `output.kill_hotkey` ends the session. Any backend that can move the real cursor refuses to start unless a keyboard listener is running. Trade-off: no "pause and resume"; you restart `eyeos run`. The dry-run backend needs no keyboard, so CI stays hardware-free.
- **Affine (degree-1) calibration by default, not degree-2 polynomial.** With only 9 calibration points, an affine model (5 parameters: 1 + 4 iris-offset numbers) is well-determined. `degree=2` is supported, but it needs more and cleaner points. Trade-off: less accurate for genuinely non-linear gaze-to-screen mappings, but more numerically predictable for a 9-point session.
- **The blink-hold gets a grace window, and the gaze holds through it.** A deliberate blink closes both eyes, which is exactly what Gate 1 watches for. Taken literally, Gate 1 would freeze the cursor the moment the confirm gesture starts. Instead, `pipeline.py` treats eyes closed for up to `confirmation_hold_s + 0.5 s` as the gesture. During that window it never maps closed-eye landmarks to the screen and holds the gaze where the eyes were last open, so the click lands where the user was dwelling. Past the window, Gate 1 fails honestly. `confirmation_mode: keypress` turns the window off. Trade-off: some complexity in `pipeline.py`, while `gates.py` stays a simple state machine you can test with a fake clock.
- **The synthetic eval fixture is generated, seeded, and committed, not recorded.** `eval/generate_synthetic.py` builds a deterministic session entirely from hand-built landmark geometry: calibration, noisy on-target dwells, a long unconfirmed hold, and five looking-away modes. It uses no video and no third-party data, is reproducible with one command, and is small enough to commit. Trade-off: it validates the pipeline's *logic*, not real-world accuracy, and as Results shows, it can expose real design problems.
- **MediaPipe's legacy `solutions.face_mesh` API, not the Tasks `FaceLandmarker`.** It needs no separate model download. Trade-off: upstream removed it in 0.10.30, so the live extra is pinned below that (Python ≤ 3.12). A port would sit behind the same `InputSource` interface and touch no other module.
